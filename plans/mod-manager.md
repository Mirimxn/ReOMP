# ReOMP Mod Manager implementation plan

## Scope and ownership

Build the desktop app in [`apps/mod-manager/`](../apps/mod-manager/) using the existing React and Tauri scaffold. Rust owns package validation, persistence and filesystem changes. React renders the inventory, deployment state and errors, and invokes the same backend operations on both platforms.

- **Game targets** shows Steam and Epic separately on Windows, and Steam via Proton on Linux. Each target has a game directory and an on/off toggle. All enabled targets receive the same enabled mods and versions.
- **Mods** shows the local ZIP inventory, with enablement and a version selector for each mod. Drag-and-drop and the file picker both accept a batch of ZIPs and call the same import operation.
- **Game assets** browses the selected installation and builds asset replacement ZIPs in the manager's own interface.
- **Input settings** uses the saved bindings shared with the single in-game input menu. Implement this screen once the input mod plan defines where bindings live, how actions are discovered and how both editors save changes. Core mods use the ordinary mod package and dependency rules.

The [platform installers](installer.md) install the desktop app. The app ships with the OMP payload and manages its deployment. On first run the manager creates a local archive directory under its per-user app data directory and records the absolute path as `installedMods` in [ReOMP's global configuration](../config/reomp.schema.json). Use Tauri's app config and data directories. Report an invalid or inaccessible configured path in the UI. Store the shared enabled IDs and version overrides, target paths and toggles, and per-target deployment receipts separately from the archive inventory. Derive the inventory from disk.

## Packages and versions

1. Use the [existing package layout](../notes/omp/mod-packages.md). A ZIP contains one top-level folder named with the exact mod ID. Its `mod.json` has `name`, optional `description`, required `version`, `actions` and `dependencies`. Each dependency entry has the provider's exact `id` and required `minVersion`. Use an empty array for a mod with zero dependencies.
2. For the initial manifest format, use three non-negative numeric components in `MAJOR.MINOR.PATCH` form, without leading zeros. Compare components numerically. A dependency on `1.2.0` is satisfied by `1.2.0`, `1.10.0` or `2.0.0`. Mod authors own backwards compatibility. The manifest has no compatibility declarations or separate API version.
3. Show only the name, description and version as mod metadata in the UI. Keep optional `mod.md` in the package as documentation for mod authors.
4. Validate ZIP paths before extraction. Reject extra roots, duplicate paths, traversal, absolute paths, links, Windows-reserved names and entries that collide after case folding or Windows path normalisation. Preserve the exact mod ID for dependency lookup and reject enabled IDs that would resolve to the same deployed directory.
5. Keep multiple versions per ID. Treat identical ZIPs with the same ID and version as one package. If different ZIPs claim the same ID and version, show the conflicting files and block deployment of that version. Stage manager imports beside the archive store destination and publish complete ZIPs by rename. Validate the whole import batch before publishing it. Copying a ZIP into the library makes it available for selection.
6. Start a native filesystem watcher before the initial scan, then reconcile queued events. Debounce create, change, move and delete events for ZIPs, ignore access-only events, and recheck a file that is still being copied before reporting it as invalid. Rescan on watcher overflow or reinitialisation. Report watcher failures with Retry. Use event notifications while the app is open and reconcile on startup. [Rust notify documentation](https://docs.rs/notify/latest/notify/)

The current [OMP manifest reader](../workspaces/dotnet/runtime-engine/src/ModInfo.cs) and [dependency reader](../workspaces/dotnet/runtime-engine/src/ModDependencyInfo.cs) supply the runtime fields. The manager enforces version rules before deploying. Apply the new manifest fields to new mod packages as they are authored. Existing repository mods are covered by the separate replacement work.

Import the installer-bundled core mod ZIPs into the library on first launch and import newly bundled versions after an app upgrade. Use the normal import checks and keep existing enablement and version overrides. A user can create and import a local core mod through the same ZIP flow and dependency rules.

## Game assets and replacement mods

1. Add a Game assets view using the manager's React components. Select a configured installation, browse a folder tree and search by path or extension. List entries in the installed PC DAT/DAT2 archives and loose asset files, and show which archive or loose location each result came from. Keep duplicate paths visible as separate sources. Extract selected originals to a user-selected destination. Keep reads confined to the selected installation and preserve the archives.
2. Implement a native Rust DAT v13 reader in the Tauri backend using the [BrickVault reference and format notes](../apps/mod-manager/reference/brickvault/README.md). Read indexes without decompressing data. Use an in-memory index keyed by installation and invalidate it when the archive list, lengths or modification times change. Build it off the UI thread. Resolve an extraction request by archive and entry ID on the backend. Use checked offsets, bounded buffers, and temporary files renamed after successful decoding. Keep the reader and authoring code separate so browsing works before the runtime provider exists.
3. Use the same native extraction code on Windows and Linux. Copy raw chunks directly. Implement the `ZIPX` RC4 transform from its format rules. Use `oozextract` 0.5.7's `Extractor::read_from_slice` for `OODL` after the licence and output checks below. Verify decoded bytes against BrickVault or the game's installed decoder on Windows. The first extraction milestone covers raw, `ZIPX` and `OODL`; list other entries and allow selecting them as replacement destinations. Show the codec when extraction is unavailable. For DLC extraction, add `LZ2K` using the linked decoder as a starting point and verify `DFLT` separately against real DLC chunks before enabling it. Check the licences of decoder code and its upstream before packaging. The BrickVault Windows DLL path is the local comparison reference. [oozextract source and licence declaration](https://github.com/lvlvllvlvllvlvl/oozextract/blob/master/Cargo.toml) · [LZ2K reference](https://github.com/stryderjoe/tt-oldera-tools/blob/main/tools/lz2k.py)
4. From an asset result, start or add to an asset replacement draft. The selected entry supplies the exact game path. The author picks a replacement file or drops it onto the draft. Support several replacements in one ZIP. Show the destination and chosen file for each entry. Ask for the mod name, version and optional description, generate a stable portable mod ID for the draft, and default a new draft to version `1.0.0`. The workflow takes replacement files as input and produces the mod without requiring code or manifest editing.
5. Generate a normal ZIP with one mod folder, the supplied replacement files, and the `mod.json` actions and dependency from the [asset replacement contract](mods/asset-replacement.md#package-contract). **Export ZIP** saves a shareable file. **Add to library** uses the normal import path. Enabling uses the same dependency, path collision and game-close checks as any other mod. The selected browse target supplies the authoring catalogue. Deployment checks the declared game paths and prepares the manager-owned replacement copies for every enabled target under the same receipt and rollback rules.
6. Verify browsing against real Windows archives. Compare paths and extracted hashes for at least one file per supported codec, including a multi-chunk entry. Exercise truncated indexes, invalid offsets, duplicate paths, and an unavailable codec. From the UI, build a two-file mod, export and reimport it, enable it, check that the game loads the replacements, then disable it and confirm original lookup resumes. Check archive hashes before and after. Linux runtime verification follows with Linux users.

## Selection and automatic deployment

1. Resolve each enabled mod to its highest installed version by default. A per-mod override selects an exact installed version until cleared. Show the selected and deployed versions when they differ. A missing override is an error. If an archive used by the last successful deployment disappears externally, keep that deployment and show the missing package. The player can restore the ZIP or select another available version.
2. Validate the entire proposed enabled set and all affected targets before applying a change. Every dependency must be enabled and resolve to at least its minimum version. Block missing dependencies, cycles, ambiguous packages and actual file collisions. Show the affected mod or target and what needs to change. Apply the same checks when importing an update, changing enablement or a version override, removing a package, or changing a target toggle. A valid ZIP can be in the library while its deployment is blocked.
3. When a newer ZIP becomes available for an enabled mod without a version override, automatically deploy the validated selection to every enabled target. A failed validation leaves the previously deployed versions in place and shows the error. ZIP additions leave the set of enabled IDs as selected in the UI.
4. For every change that touches game or prefix files, if any affected game is running, show **Waiting for the game to close** and defer the whole change. Apply it automatically once all affected games close. Recheck the latest requested state, archives, targets and game status before writing. Persist the pending request and resume the check on next launch if the manager closes. Keep a single deployment operation in flight so changes and watcher events cannot start competing writes.
5. Show deployment errors in the manager with **Retry**. Include the failed operation, affected target or mod and the reason. Retry rechecks the current files and dependencies, then uses the same game-close gate. A failure stops automatic attempts for that request until Retry or a relevant change supersedes it. The previous deployment stays active after successful rollback. If rollback cannot finish, show the recovery error and make Retry resume recovery before any new deployment.

## Game targets and OMP payload

1. Use launcher metadata to suggest game paths. For Steam, use its library list and `appmanifest_920210.acf`. For Epic, read the launcher installation manifests. Offer a game-folder picker for each target when discovery fails or the user wants to correct the path. Validate the folder against `LEGOSTARWARSSKYWALKERSAGA_DX11.exe`, canonicalise it and reject Steam and Epic entries that resolve to the same installation. [Epic launcher manifest location](https://dev.epicgames.com/documentation/en-us/unreal-engine/academic-installation-of-unreal-engine)
2. Stage a versioned OMP release payload in the manager's Tauri resources at build time. Package the proxy DLL, driver, driver config, runtime engine and bundled .NET runtime from the [OMP release packaging](../scripts/package-release.ps1). Include a payload file list and hashes. Have the Windows package build and Linux container build consume the same staged Windows game-runtime files from the matching OMP build. Fail packaging when required payload files are missing. [Tauri resource bundling](https://v2.tauri.app/develop/resources/)
3. On Windows, find game processes by executable name, then match their full executable path to the affected targets. Treat a matching process with an unreadable path as potentially running. On Linux, match the Proton game process by executable name and Steam app or prefix information available under `/proc`. If the process matches the game but its target is uncertain, wait for it to exit. Check on deployment requests and while a request is pending. [Windows executable path API](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-queryfullprocessimagenamew)
4. On Linux, use the selected Steam library's existing `steamapps/compatdata/920210/pfx` by default. If it is absent, show that the player needs to launch the game once through Steam, then offer Retry. Bind all prefix changes to the verified game prefix. Set `dinput8` to `native,builtin` under `HKCU\Software\Wine\AppDefaults\LEGOSTARWARSSKYWALKERSAGA_DX11.exe\DllOverrides`. List the required prefix files in the bundled payload metadata. Start from the [existing Steam Deck setup](../installers/linux/setup-linux.sh) for runtime placement. Bundle any Wine shim only for a payload that requires it. For registry writes, wait until Wine has finished writing the prefix registry and preserve unrelated values. Track the previous override and any replaced prefix file so they can be restored when the target is turned off. [Valve Proton FAQ](https://github.com/ValveSoftware/Proton/wiki/Proton-FAQ/9a1684b9b948a44c8b7fda0c32d2fa50f8956bb4)
5. When turning a target on, replace an existing OMP installation. Move its previous `mods/` to a unique backup directory inside `<game>/legacy-mods/`. Keep previous known OMP binaries only as temporary rollback data and delete those copies on commit. Identify legacy files from known layouts and bundle evidence. If a path such as `dinput8.dll` is occupied by a file the manager cannot identify as OMP, show a collision error and leave it alone.
6. Deploy enabled packages as unpacked folders under `<game>/mods/<mod-id>/`. OMP discovers them on the next launch. When turning a target off, remove only the game files the manager owns and undo its recorded prefix changes. Keep legacy backups and the shared ZIP library. [OMP mod discovery](../workspaces/dotnet/runtime-engine/src/RegisterMods.cs)

## Safe apply and recovery

- Keep a receipt per target with the canonical game and prefix paths, OMP payload version, deployed mod IDs and versions, owned paths and file hashes, and prior values for changes that must be restored. If an owned path or setting has changed since deployment, stop before overwriting or deleting it and identify it in the error.
- Stage validated files on each destination filesystem outside the live `mods/` directory. Record a durable transaction journal with the planned renames, previous state and recovery paths. Recheck that affected games are closed immediately before changing live files. Move replaced files to transaction storage and publish staged files by rename. Keep rollback data until every affected target has succeeded.
- Publish the new receipts and effective shared state only after all targets succeed. If any target fails, reverse the changes on every target touched. On startup, finish cleanup for a committed journal or recover an interrupted deployment before accepting writes. Keep the pending or failed request visible separately from the last successful deployment.

## Implementation and verification order

1. Implement the Rust package reader, local library, watcher and version resolution. Use Windows fixtures for a real import batch, a duplicate ID and version with different bytes, an invalid ZIP path, a missing dependency, a dependency cycle and a newer major version satisfying a minimum. Verify a ZIP copied into the watched directory appears in the inventory without refreshing.
2. Implement receipts, staging, recovery and the Windows target adapter. Use temporary game folders for two targets. Check that each toggle affects only its target, the same shared selection is installed on both, old mods move to `legacy-mods`, and an unknown proxy file is left intact. Inject a failure during the second target's write and check both targets and their receipts roll back. Restart the manager during a staged transaction and check recovery.
3. Connect the React flows. Use both drag-and-drop and the file picker. Import a newer version with a game open and verify that both targets keep their prior files until it closes, then receive the update automatically. Verify that a pinned mod stays on the chosen version. Force a recoverable deployment error, confirm the UI shows it, fix the cause and use Retry. Check that Retry while the game is open waits for it to close.
4. Implement Game assets indexing and extraction in Rust, then the browser and draft editor. Verify the reader with fixtures first. Connect ZIP generation and enabling after the asset provider and its deployment contract pass the Windows replacement check.
5. Run `npm ci`, `npm run build`, `cargo test --locked --manifest-path src-tauri/Cargo.toml` and `npm run tauri build -- --debug --no-bundle` from the manager directory. On Windows, verify a real game launch through Steam and through Epic where an installation is available. Record which targets actually launched.
6. Implement the Linux adapter and include its payload in the Linux build from the [installer plan](installer.md). Record whether the build produced the app with the expected payload. Linux runtime verification comes later from Linux users, including discovery, prefix setup and removal, deferred deployment under Proton, and browsing and extracting game assets.
